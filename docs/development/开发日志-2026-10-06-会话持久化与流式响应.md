# 开发日志：会话持久化与流式响应

日期：2026-10-06  
状态：设计中，尚未实现或验收。

## 本次确定的基础接口方向

面试后端维持一个 FastAPI 应用和一个由 Runtime 持有的 compiled graph。每次初始化面试时生成唯一 `session_id`；该 ID 同时作为 LangGraph 的 `thread_id`，用于保存和恢复这一场面试独有的 `TaskState`。

预期的最小闭环：

```text
POST /interview/init
    -> 创建 session_id
    -> 写入候选人、面试官等初始 TaskState
    -> 返回 session_id

POST /interview/message（携带 session_id）
    -> 读取该 session 的 TaskState
    -> 执行 Graph
    -> 保存更新后的 TaskState
    -> 返回本轮结果
```

不同 session 共享 Graph 定义、模型配置和状态保存器，但不共享候选人信息、对话消息、轮次或评估结果。`thread_id` 是 LangGraph 的持久化会话键，不是 Python 操作系统线程编号。

本条仍是设计：尚未通过 Insomnia 验证同一 `session_id` 的连续状态续接，也尚未验证不同 ID 的状态隔离。

## 暂不实现：线程池与同会话并发控制

当前目标是先跑通普通 HTTP 的 init/message 接口，不引入线程池。

原因：一场面试在用户输入间隔中并不持续执行；收到消息请求时才产生短暂的异步请求任务，模型调用完成后任务结束。session 应保存状态，而不是永久占用一个线程。

后续只有出现下列证据时，再评估线程池：

- 模型 SDK 或存储库只有同步阻塞接口，且其调用发生在 `async def` 执行链中；
- 存在本地 CPU 密集任务，例如音频转码或大规模计算；
- 实测确认阻塞操作影响其他请求响应。

即使后续引入线程池，它也是服务级的有限共享资源，不是“一个 session 一个线程”。还需要单独处理同一 session 的重复提交，候选方案包括：正在处理时拒绝新消息、按会话排队、版本校验或幂等键。具体方案待接口闭环和并发测试后决定。

## 暂不实现：SSE 流式回复

当前先使用普通 HTTP 响应验证 Agent、Graph 和状态更新正确性。SSE 将在以下条件满足后再接入：

1. 普通 `/interview/message` 能稳定返回完整一轮结果；
2. 模型侧能够提供可消费的流式输出；
3. 明确前端事件协议与终止语义。

计划中的 SSE 只改变“如何把一轮结果返回给前端”，不会替代 `session_id → thread_id → TaskState` 的会话持久化机制。事件类型至少需要在实现前确定：文本增量、该轮完成、面试完成、错误。客户端断线、取消模型调用、重连恢复和事件重放均为后续单独设计项。

浏览器原生 `EventSource` 只发起 GET；若消息提交继续使用 POST，则前端需要按 POST 响应流读取，或另行设计“POST 提交 + GET 订阅”的接口组合。选择哪种方式应在前端接入前确定。
