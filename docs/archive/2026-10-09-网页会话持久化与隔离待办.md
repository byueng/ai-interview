## 要解决的问题

网页提交候选人和面试官信息后，后续消息应始终使用同一场面试的配置与历史；不同面试不能串用信息。需要分别考虑连续请求、刷新页面、新开标签页、后端重启四种情况。

不采用“每个网页创建一个 FastAPI app”。应用和 Graph 可以共享，面试状态必须按会话区分。

## 已确定的职责边界

- `session_id`：业务上的面试标识，不代表用户身份或访问权限。
- `configurable.thread_id`：由 `session_id` 构造，供 Graph 定位这场面试的检查点。
- `TaskState`：候选人配置、面试官配置、消息、轮次等实际数据。
- checkpointer：保存和恢复 Graph 状态；不另外长期缓存 `session_id -> [state, config]`，避免两份状态不一致。
- Vue 的内存状态管理负责页面内使用数据；浏览器存储负责跨刷新保留标识，两者都不能替代服务端状态保存。

## 当前代码事实（本次只记录，不修复）

- `src/frontend/src/api/candidate.ts` 已有内存缓存和 `sessionStorage`，但 `initializeSession()` 会先清除缓存再请求新 ID；不能据此认为刷新恢复已经完成。
- 前端调用 `/interview/init`、`/interview/candidate_config`；当前后端路由是 `/interview/begin`、`/interview/personal_information_config`，接口契约仍需统一。
- `src/backend/interview_service.py` 的 `create_session()` 只生成 UUID，没有保存初始配置。
- 个人信息配置接口仍是占位实现；`run_turn()` 已按 ID 构造 config，但会话存在性、配置完整性检查未完成。
- Runtime 使用 `InMemorySaver`：不具备后端重启后恢复或多个 worker 共享状态的能力。
- SSE 已有事件包装，但它只负责响应传输，不解决面试状态续接。
- 本次模拟测试读取检查点时，LangGraph 提示 `schemas.Candidate`、`schemas.Interviewer` 未在序列化允许列表显式注册，未来版本可能阻止恢复。后续持久化任务需处理并验证，不在本次绕过或扩大反序列化权限。

## 恢复此任务时需要确认

1. 一场面试的生命周期：刷新继续、主动新建重置、结束与过期后如何处理。
2. 标签页隔离：是否每个新标签页都创建新面试。`sessionStorage` 通常按标签页隔离，但通过 opener 打开的页面可能获得初始副本，不能只靠存储位置保证新 ID。
3. 统一初始化、配置、消息接口的路径、请求体、返回值和 session_id 传递方式。
4. 初始配置写入、恢复历史、会话不存在和配置不完整时的错误行为。
5. 同一会话的重复提交与并发请求如何控制。
6. 如需重启恢复/多 worker，选择持久化 checkpointer；如引入用户登录，增加会话归属校验，不能把知道 UUID 当成授权。

## 后续验收

- A、B 两场面试采用不同配置，交错发送消息，回复和历史互不混淆。
- 同一 ID 的下一条消息继续使用已有配置和历史。
- 刷新、新标签页、主动新建的行为符合确认后的约定。
- 不存在、过期、未配置、无访问权限的会话按约定处理。
- 后端重启与多 worker 的行为符合所选存储方案。

这些条目尚未完成端到端验收。本次单次 Agent 测试不代表以上能力已实现。
