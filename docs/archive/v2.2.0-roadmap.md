## 2. P0：完整面试流程与多 Agent 渐进式评估

### 当前实现与迁移目标

当前状态（2026-10-29 主目录代码核对，非全链路验收）：Graph 在启动时构建，每轮请求以同一会话的 `thread_id` 运行，检查点衔接多轮状态；有效路径仍为 `START → InterviewAgent → END`。`AssistantAgent` 已注册但未连接；`ResumeAgent` 已有占位类和提示词目录，尚未形成可执行协作节点。简历分析仍由 `InterviewAgent.sync_resume` 调用，结果为单段 `resume_evalute`；提问时仍传入完整 `state.messages`。当前 `END` 结束本轮运行，不代表整场面试结束。

目标：以一场面试为单位，由 ResumeAgent 和当前代码中的 InterviewAgent（职责名称 InterviewerAgent）围绕结构化共享评价协作。简历按主题逐步展开，回答作为新证据进入评价，持续决定追问、换题或结束。共享评价应代表可修正的当前理解，并能追溯依据；不要求将完整历史反复放入每个 Agent 的提示词。

“一次面试一次 graph”指一个持续的逻辑流程：同一 `thread_id` 下通过暂停与恢复推进，允许每轮单独发起 HTTP 请求和图恢复调用，不要求每场重新编译 Graph 或保持一条长连接。改成循环图本身不保证节省 token；成本由上下文装配、模型调用次数和输出量共同决定。

以下六阶段均为待实现设计，讨论确认及文档更新不视为功能完成。依赖顺序为阶段 1 → 2 → 3 → 4；阶段 5 的记忆作用域在阶段 1 确定，跨场存储按需实施；阶段 6 的指标从迁移前建立基线，调度优化在协作流程稳定后进行。

### 阶段 1：共享评价与更新契约

- [ ] 以 `topic_id` 标识考察主题，定义简历依据、考察目标、优先级及理由、回答证据、当前判断、不确定点、下一步建议、执行状态和版本；主题状态覆盖待考察、进行中、已覆盖、暂缓。
- [ ] 明确区分简历自述、候选人回答、Agent 推断与待验证假设；证据引用片段 ID、问题 ID、回答 ID 和轮次。当前判断可被新证据修正，保留修正依据，不把一次未答出升级为永久能力结论。
- [ ] 明确字段写入责任：系统记录原始问答，ResumeAgent 提议更新证据关联、判断和建议，InterviewAgent 记录所选主题、实际问题、提问目的及执行状态；用确定的更新规则合并，避免两个 Agent 覆盖整份评价。
- [ ] 定义重复事件去重、旧版本更新、建议已执行、证据冲突及信息不足的处理；首版顺序更新，后续并行时再定义 reducer 和版本冲突策略。

验收：用一个完整样例推演“简历声明 → 发现考察点 → 提问 → 回答证据 → 修正判断 → 继续／结束”；能够追溯判断来源，重复回答不会重复加分，矛盾证据不会被静默覆盖。

### 阶段 2：简历分层与按需阅读

- [ ] 将简历组织为整体概览、项目／经历／技能的主题摘要、原始片段三层；按语义边界切分，保留片段归属和稳定 ID，避免只按固定字数破坏经历上下文。
- [ ] 区分一次性本地 PDF 文本提取与模型理解：提取原文后缓存，ResumeAgent 首次获得必要的整体视野和初始重点，之后按主题读取相关片段；不把所有切片重新拼回每轮提示词。
- [ ] 定义 Agent 输入视图：ResumeAgent 读取相关简历片段、新增回答及相关评价；InterviewAgent 读取当前考察目标、必要背景、关键证据、短期对话及候选建议，按需请求展开原文。
- [ ] 按文件内容／版本管理解析和摘要缓存，重传不同简历或变更岗位时使相应派生结果失效；先用片段 ID、标签和主题关联检索，向量库在规模和召回需求明确后评估。

验收：短简历和多项目简历都能保留必要背景；相同材料不重复解析，相关片段可回溯；记录实际模型输入量，确认按需加载而非仅完成“切片”形式。

### 阶段 3：两 Agent 协作闭环

- [ ] 接入 ResumeAgent：提出值得深挖的主题和理由，结合新回答更新简历与候选人的当前评价，输出结构化变化及追问建议。
- [ ] 接入 InterviewAgent：结合建议、岗位、已覆盖主题及剩余预算选择本轮目标，组织问题；记录建议的采用、暂缓或完成状态，避免重复推荐和重复提问。
- [ ] 建立基本路径：初始重点 → 共享评价 → 选择主题并提问 → 接收回答 → 记录证据 → 更新判断与建议 → 追问／换题／总结。普通逻辑使用函数节点，不为每个步骤额外增加模型 Agent。
- [ ] 定义面试覆盖要求、主题结束、整场结束及信息不足条件；最终评价引用已取得的证据。辅助总结、AssessAgent、EvaluateAgent 的必要性在闭环稳定后再确定，旧版评分不算已迁移。
- [ ] 覆盖模型失败、无法形成有效建议、重复提交和人工结束；验证失败不会提前推进主题或轮次。

验收：用至少两个主题完成由浅入深的面试，ResumeAgent 能因新证据修改建议，InterviewAgent 能据此改变问题；结论和提问路径可回溯，内部协作不产生无界循环。

### 阶段 4：整场面试的暂停与恢复

- [ ] 将本轮 `END` 模式迁移为整场逻辑流程：初始化 → 规划 → 提问 → 等待回答 → 评价更新 → 下一题，只有满足整场终止条件才完成面试。
- [ ] 使用同一 `thread_id`、checkpointer、`interrupt()` 和 `Command(resume=...)` 衔接多轮请求；保留会话隔离、轮次校验与重复提交保护。
- [ ] 拆开问题生成和等待输入节点；考虑中断节点恢复时从头执行，防止重复模型调用、重复发题或重复写入证据。
- [ ] 明确开场、提问、澄清、等待回答、评估、总结、结束的输入输出、允许迁移和失败行为；新增主动开始面试的接口与 UI。
- [ ] 对齐 SSE 与前端状态：本轮输出完成、等待用户、内部分析中、整场结束分别表达；断开连接不自动等于结束面试。
- [ ] 结合第 4 节实施持久化检查点及恢复验收；核对既有 `resume_evalute`、轮次字段和活跃会话的迁移／重建策略，保留每阶段回退边界。
- [ ] 重新验收开场与简历任务时序。历史清单曾在 2026-10-28 勾选“开场后才读取简历”；2026-10-29 代码显示首轮会启动后台分析、但不等待结果，二者不等同。目标先保证开场不被深度分析阻塞，具体读取时机需明确并测试。

验收：首次启动、连续回答、暂停后恢复、断流重连、重复恢复和主动结束均有明确状态；无重复问题及证据写入；进程重启恢复单独验收，不能用进程内恢复代替。

### 阶段 5：共享工作记忆与长期记忆

- [ ] 首先将本场主题、证据、当前判断和建议保存在会话级 State，由 checkpointer 管理；为每个 Agent 单独装配需要的上下文，共享存储不意味着全量提示词共享。
- [ ] 在存在跨面试需求时再引入 Store：区分同一候选人的持续能力证据与可供其他面试复用的经验，定义候选人／会话／岗位作用域及访问规则。
- [ ] 长期条目记录来源、适用范围、时间、版本与更新原因，支持纠正和失效；个人评价不会自动进入公共经验库，模型建议需经过验证才提升为复用经验。
- [ ] 明确何时写入、合并、检索及删除；评估 LangMem 或其他记忆组件时，以实际缺口为依据，不将接入组件等同于完成记忆治理。

验收：本场记忆能支持两 Agent 协作且不会跨会话串用；若启用长期记忆，验证跨场检索、范围过滤、证据引用和错误判断纠正。未启用时明确记为后续扩展。

### 阶段 6：调度、token 与延迟预算

- [ ] 在旧流程建立延迟、模型调用次数、输入／输出 token 基线，同时记录重复提问和有效证据覆盖；比较时固定简历、回答场景及模型配置。
- [ ] 定义 ResumeAgent 触发条件：新证据、矛盾、主题切换或阶段总结；普通澄清可复用已有建议，避免每个节点、每条消息都触发两个模型。
- [ ] 限制每轮内部协作次数、上下文预算和输出长度；更新只携带新增回答与相关主题，结合当前判断和近期原话，旧证据通过引用按需加载。
- [ ] 可在用户作答期间预分析其他主题，但依赖本次回答的评价必须等待回答到达；后台结果携带主题和状态版本，过时结果不得覆盖新判断。
- [ ] 对短简历和复杂简历分别比较成本与质量，设定可接受的延迟及预算；预算耗尽时按明确策略结束深挖、换题或给出信息不足结论。

验收：提交迁移前后同场景的延迟、token、调用次数、重复提问、有效证据覆盖和判断修正记录；成本优化不能以丢失关键证据为代价，未经测量不宣称“多 Agent 更省 token”。

扩展边界：先稳定上述状态机与评价标准，再抽取可复用 Skill；MCP 与 Harness 在出现外部服务或受控执行需求后另行评估。

设计参考：[LangGraph State 与 reducer](https://docs.langchain.com/oss/python/langgraph/graph-api)、[中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)、[checkpointer 与 Store 边界](https://docs.langchain.com/oss/python/langgraph/persistence)。API 落地时以项目锁定版本验证。

## 4. P1：中断、恢复与持久化

此节与第 2 节阶段 4 联动；选择整场面试可恢复流程后，相应恢复能力为该迁移的验收依赖。等待用户回答的图中断、取消模型调用、网络断流和结束整场面试需分别处理。

- [ ] 分别定义取消模型调用、停止发送响应和结束整场面试；验证各时机的消息、轮次、取消传播及可继续性。
- [ ] 完善断流后的同步与用户提示，避免未确认回复被重复提交。
- [ ] 如需跨重启恢复或多 worker，实施持久化检查点、数据迁移与恢复测试；当前仅进程内恢复。
- [ ] 如引入账户体系，实现会话归属与访问控制；UUID 不能作为授权。
