## 1. 基础链路与异常处理

状态：已有会话初始化、配置写入和单轮对话实现，需补齐异常行为并回归验证。

- [ ] 验证“创建会话 → 写入配置 → 连续多轮对话”，确认历史消息、配置和轮次正确续接。
- [ ] 明确不存在、未配置、结束或失效会话的处理规则，避免直接访问缺失字段。
- [ ] 统一预设保存、快照导出和图执行失败的处理边界，检查 `message`、`error`、`done` 事件行为。
- [ ] 完善文件读写异常处理和快照父目录初始化，验证写入失败不会被误报为成功。
- [ ] 复核请求字段与实际业务使用的一致性，明确 `role`、`chat_round`、`dtime` 的职责。
- [ ] 回归现有自动化测试，并分别记录模拟测试、真实模型调用和完整 HTTP 业务验收的结果与日期。

验收依据：保存请求条件、事件序列和状态检查结果；不能仅以 HTTP `200` 或模型生成过一次回复作为完整验收结论。

## 2. 会话隔离与生命周期

状态：已按 `thread_id` 管理进程内状态；生命周期约定和并发策略尚需明确。

- [ ] 使用不同配置创建 A、B 两个会话，交错发送消息，检查历史和回复是否串用。
- [ ] 确定同一会话重复提交及并发请求的处理策略，并验证状态与轮次一致性。
- [ ] 明确主动新建、继续、结束与过期的语义，以及后端重启后旧会话 ID 的处理方式。
- [ ] 在后端规则确定后，联调刷新、新标签页和主动新建的会话行为；不直接沿用历史待办中的前端状态结论。
- [ ] 处理检查点恢复时 `Candidate`、`Interviewer` 类型的序列化兼容性警告，并验证恢复过程；不通过扩大反序列化权限绕过问题。

条件性计划：如需跨重启恢复或多 worker 部署，再选择持久化检查点方案并测试；如引入账户体系，再设计会话归属和访问控制，不能将持有 UUID 视为授权。

## 4. Agent 能力扩展

状态：设计中，尚未接入执行图。

### 4.1 技术定位与实施顺序

当前目标不是堆叠 Prompt、MCP、Agent、Skill 与 Harness，而是让每一层解决明确的问题。已存在的单轮 `InterviewAgent`、`TaskState` 与 LangGraph 执行图是后续扩展的基础，但不代表下列设计已完成。

- [ ] 以“状态机约束下的单 Agent”作为当前主线：由确定性流程控制开场、提问、澄清、追问、结束和评估阶段；模型只承担回答理解、内容生成及受限的下一步建议，不能自由决定整个业务流程。
- [ ] 为每个面试阶段定义输入、允许状态迁移、输出结构、终止条件和失败处理；用正常、信息不足、重复提交及模型失败样例验证迁移结果。
- [ ] 保留 Prompt 作为阶段行为与上下文的配置方式，避免将 Prompt 模板本身表述为独立的 Agent 能力。
- [ ] 在单 Agent 流程和评价标准稳定后，再将岗位题纲、追问策略、评分 rubric 等可复用领域能力抽成 Skill；明确每个 Skill 的输入、输出、版本和测试样例。
- [ ] 暂不引入 MCP：只有需要以标准协议访问外部招聘系统、日历、知识库或其他独立服务时，才评估工具发现、鉴权、最小权限和调用审计。
- [ ] 暂不引入 Harness：当前浏览器面试应用没有执行命令、操作文件或运行长任务的需求；若后续引入此类受控执行环境，再单独定义沙箱、资源回收和安全边界。

验收依据：给出状态迁移记录与结构化输出，验证模型异常、无效输入或重复请求不会让会话错误推进；仅能生成一次回复或串接多个 Prompt 不构成流程 Agent 的验收。

- [ ] 面试轮次先后不对，应先是面试官开启面试，而不是面试者先发送信息，另需要开始面试的接口和前端UI来启动。
- [ ] 设计并实现 `AssiantAgent`：随面试推进整理回答，为面试官追问提供参考。
- [ ] 明确总结的触发时机、输入输出、保留粒度和状态更新方式，再通过实际回答样例验证效果。
- [ ] 明确 `AssessAgent`、`EvaluateAgent` 的职责及接入时机；不将旧版评分能力视为已自动迁移。
- [ ] 补全简历上传、解析与上下文接入流程；区分文件路径和实际简历内容。
